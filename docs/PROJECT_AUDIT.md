# Project audit — 3.1.2

Baseline: released 3.1.1 (`1c2a751cbaf4feb6be7d081cf89b4a52ae43e867`). Reviewed the tracked application Java/AIDL, manifest, resources and translations, tests, Gradle configuration/wrapper settings, CI/release workflows, scripts, documentation and bundled license notices. Generated build outputs and private signing material are outside the source review. Third-party dependency internals were not audited or upgraded as part of this pass.

## Fixed with evidence

| Finding | Before | Change and verification |
| --- | --- | --- |
| Stale network callbacks | A callback queued before unregistering could still invalidate newer state. A superseded probe could overwrite the latest loss event. | `PushRuntime.java` checks callback identity and the active network, serializes callback/result publication on the main thread, and checks the network revision before accepting results. Device regression exercises retired callbacks; real GMS tests exercise network loss/restoration. |
| Unbounded duplicate refresh work | Repeated provider/resume events queued independent refresh jobs. | Coalesce refresh work into one active job and one pending refresh. |
| Missed or stuck app scans | Refresh requests arriving during a scan were dropped; an unexpected runtime failure could leave the scanning flag stuck. | Queue a follow-up scan, reset state on failure and retain existing results with a retry message. |
| Repeated work for every app | The same comma-separated system list was parsed for every row; app identity and reflective method lookups were repeated. | Parse once per scan, obtain each app's UID once and cache method discovery. Read outcomes still remain independent and unknown when unavailable. |
| UI work while hidden | The activity stayed subscribed to runtime changes until destruction, rendering and potentially rescanning while stopped. | Subscribe only between `onStart` and `onStop`; resume still explicitly refreshes state. |
| Recovery entry depended on unrelated notifications | Recovery extras were consumed by the state-change listener rather than the launch path. | Consume them on creation/new intent and enqueue the request immediately. Device regression verifies consumption before observer notifications. |
| Partial recovery broadcasts | An exception sending GTALK heartbeat also skipped MCS for that package. | Isolate all five targeted attempts; a rejecting-context regression verifies later attempts still run. No request is presented as confirmed reconnection. |
| IPv4 route omitted | The first two DNS answers could both be IPv6, omitting a working IPv4 route. | Probe the first address from each family while preserving resolver preference and bounded work; pure-Java regression covers this case. |
| Contradictory GMS dumps | Another service before the GMS section bypassed the single-service check; contradictory legacy/current fields were accepted. | Require exactly one service and agreement between current fields; fixtures verify both failures remain unknown. |
| Partial subprocess reads | An I/O error draining command output was silently ignored. | Reject a failed drain as `READ_FAILED` rather than parse a potentially incomplete reply. Existing limits on time/output remain. |
| Helper attached after disabling | A late connection callback could retain a helper after enhanced checks were switched off. | Recheck preference and authorization before accepting it; device regression injects a late callback. |
| Retired privileged/code paths | The obsolete socket query, list-append helper, broad global Autostart route and old theme override API remained. | Remove dead APIs/tests; retain AIDL transaction IDs 0, 2 and 3 without reusing retired ID 1. Fixed read-only command failure classification now has its own tests. |
| Obsolete UI resources | 120 unused string names remained, including old whitelist writes, notification protection and language-selection copy. | Remove all localized definitions of those names, three unused layout/icon files and an unused style. Retain current translations and license notices. Correct count-label grammar and redundant background painting. |
| Release identity/gating | The manual signing workflow accepted any valid certificate and could publish before device checks passed. | Require successful `build-apk.yml` for the exact source SHA; verify the established certificate, embedded source SHA and non-debuggable APK before publishing. The CI-query command was checked against a successful source run. Executing the secret-backed manual signing workflow still requires the owner's configured signing secrets. |
| Device test scripts could modify a real phone | Quick-settings smoke tests install/uninstall the package and change system settings. | Require a disposable emulator before mutations; screenshot capture applies the same restriction. This does not restrict normal APK use on physical phones. |
| ABI checker memory/packaging | Reading a native library decompressed the entire file just to inspect 20 bytes; mislabeled ABI directories were accepted. | Read only the ELF header and validate its directory against the machine type. Four Python tests cover neutral, valid, 32-bit, mislabeled and corrupt inputs. |

### Original review findings (3.1.2 baseline; current decisions above)

1. **Default branch/release mismatch (high operational priority).** At review time `main` was `ec75d56384e519cfd9d79be686a8c7b1ffd7a3cf`, while the released application was on the newer history in draft [PR #2](https://github.com/maixuanfeng1/FCMGuard-HyperOS/pull/2). Releases point to exact tested commits, but cloning `main` or dispatching its old release workflow does not build the current app. Review/merge that source history before treating `main` as current. This audit does not merge or rewrite `main`.
2. **HyperOS/GMS compatibility (needs physical-device evidence).** `GmsConnectionState`, `AutostartStatusReader` and `HyperOsSettings` depend on private GMS fields/vendor AppOps/OEM component routes. A successful settings launch cannot prove the OEM page honored every extra. The tested GMS schema is 26.11; an unsupported version must stay unknown. Verify current HyperOS 4, app-specific settings routes, autostart status, VPN/split-routing and locked-screen delivery on the actual phone. Emulator success does not establish notification delivery.
3. **Release size/R8 (medium).** `app/build.gradle` keeps shrinking disabled. Enabling R8 could reduce the APK substantially, but the Shizuku helper constructors and AIDL/reflection entry points need explicit retention and signed-release tests with actual Shizuku. Keep it disabled until that work is done; dead-resource cleanup alone is not a multi-megabyte optimization.
4. **Large app lists/UI state (medium).** `MainActivity.renderApps` still rebuilds a `LinearLayout` with all visible rows, and resume performs a fresh scan. RecyclerView, package-change-driven caching, saved expansion/scroll state and preserving those states across theme recreation are possible improvements. Choose these if large lists feel slow; the fixes above remove repeated parsing/lookup work without changing navigation or scan freshness.
5. **Language coverage (medium).** Current diagnostics provide English and Chinese; other system languages fall back to English for most new text. Much of the Traditional Chinese diagnostic copy is still Simplified Chinese. Confirm supported languages and have translations reviewed rather than treating legacy translated theme labels as complete coverage.
6. **Minimum SDK policy (low, explicit choice).** The APK still declares minSdk 24, while device CI intentionally tests only Android 17, per the owner's requirement. Either retain broader best-effort compatibility with that limitation or raise the minimum in a separately reviewed release. No Android 15/16 tests were added.
7. **Backup/transfer policy (low).** Backup is disabled with `allowBackup=false`; newer Android supports explicit data-extraction/device-transfer rules. Decide whether preferences should transfer to another device before introducing blanket include/exclude rules.
8. **Build reproducibility hardening (low).** Direct dependencies/toolchain are pinned and the Gradle distribution is checksummed. Transitive dependency locking and immutable GitHub Actions commit pins would further constrain rebuilds, with an associated update-maintenance cost. No vulnerability claim is made without a dedicated dependency advisory scan.
9. **Continuous monitoring is a product tradeoff, not supplied by a tile.** Hidden surfaces stop their five-second refresh callbacks. Process freezing/reclamation can interrupt event-driven work. Permanent connection monitoring would require revisiting the previously accepted background-execution/notification tradeoff; it was not silently reintroduced.

## Verification and limits

Local checks: debug/release compilation, unit tests, debug/release lint, Python ABI-checker tests, shell/Python syntax checks and parsing all remaining resource XML. Device CI runs only Android 17 ATD and full Google APIs images, including real shell UID 2000 queries, GMS online/offline/restored agreement with actual Diagnostics, platform Tile states, settings fallbacks, old-record migration, return without dialogs, retired network callbacks, late helper callbacks, independent recovery attempts and SystemUI recovery after process reclamation. Exact counts and run links are recorded in the release/PR validation for this commit.

Lint findings retained intentionally: the private vendor AppOps query (unknown fallback), accessibility headings ignored below API 28, the backup/transfer decision above, and a static application-context reference. `ShizukuBridge` stores `getApplicationContext()`, not an Activity; this is not an Activity leak. No blanket warning baseline was introduced. Lint warnings fell from 131 on the baseline to five after cleanup, with zero errors.

This review fixes reproducible/static-evidence issues. It is not a proof that no defects remain, a review of Android/GMS internals, or a physical HyperOS compatibility certification.
